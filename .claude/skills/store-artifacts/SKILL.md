# Store artifacts

Everything App Store Connect asks for, produced from the app rather than
written from memory. Run it before a submission; run it again after any change
to onboarding, the chat list, Settings or `app.json`, because those are what
the screenshots show.

The artifacts live in `distribution/`. They are committed, so a diff shows what
changed about the listing and why.

```
distribution/
  privacy-labels.md        App Privacy and Data safety answers, for both stores
  capture.yaml             the Maestro flow both stores' screenshots come from
  ios/
    store.config.json      EAS Metadata: title, subtitle, description, keywords
    review-notes.md        App Review notes + the rejection risks specific to this app
    export-compliance.md   Encryption declaration, answered yes
    screenshots/6.9/       1320×2868, the size Apple requires for iPhone
  play/
    listing.md             Google Play listing text, data safety, policy risks
    icon.png               512×512, generated by `npm run brand:build`
    feature-graphic.png    1024×500, generated with it
    screenshots/           1080×1920, from an emulator resized to 9:16 for the run
```

`eas.json` points `submit.production.ios.metadataPath` at
`distribution/ios/store.config.json`; EAS Metadata would otherwise look for
`store.config.json` at the project root.

## Why it erases the simulator

Because this is a messenger. A screenshot taken against a device that has been
used holds real conversations, real addresses and real names, and the App Store
listing is the most public place those could end up. The flow starts from an
erased device and creates its own account, so everything visible is text entered
by the capture flow or content generated by the app.

That is also what makes it reproducible: same starting state, same screens,
same order.

## Run it

```bash
./scripts/capture-screenshots.sh store              # the debug build in DerivedData; Metro on :8081
./scripts/capture-screenshots.sh store path/to.app  # a release build, for the real submission
./scripts/capture-screenshots.sh play path/to.apk   # a release APK, on a booted emulator
```

The script does what used to be a checklist here: finds the iPhone 17 Pro Max,
erases and boots it, installs the build, points a debug build at Metro (the
host is read from the routing table, not assumed to be en0), runs
`capture.yaml`, collects the images into `distribution/ios/screenshots/6.9/`, and
refuses any that are not 1320 × 2868, because a different size means the wrong
simulator, and App Store Connect rejects the upload rather than scaling.

For a real submission use a release build: a debug build can show the dev
launcher, and its performance is not what a reviewer sees. A debug build is
fine for checking the flow still works.

Build the debug app with `xcodebuild -workspace ios/Statim.xcworkspace
-scheme Statim -configuration Debug -sdk iphonesimulator -destination
"id=<simulator>" build` (or `npx expo run:ios`) after `npx expo prebuild
--platform ios` and `npx pod-install`. `patches/README.md` explains why
Expo modules are built from source; a debug build with the precompiled ones
crashes at launch.

## Check the text

Apple truncates silently rather than erroring, so the limits are worth
asserting:

```bash
python3 -c "
import json
i = json.load(open('distribution/ios/store.config.json'))['apple']['info']['en-US']
for k, limit in [('title',30),('subtitle',30),('promoText',170),('description',4000)]:
    n = len(i[k]); print(f'{k}: {n}/{limit}', 'OK' if n<=limit else '*** OVER ***')
n = len(i['keywords'][0]); print(f'keywords: {n}/100', 'OK' if n<=100 else '*** OVER ***')
for k in ('privacyPolicyUrl','supportUrl','marketingUrl'):
    if 'REPLACE-ME' in i[k]: print(f'{k}: *** still a placeholder ***')
"
```

## Before submitting

These are the ones that get an app like this rejected, and none of them are
fixed by re-running the capture. Read `ios/review-notes.md`, `privacy-labels.md`
and `ios/export-compliance.md` in full; the short version:

- [ ] Organization account. Guideline 3.1.5(b) requires cryptocurrency
      wallet apps to come from an organization, not an individual. Check the
      enrollment type before building; changing it takes weeks.
- [ ] Export compliance. Each uploaded build shows "Missing Compliance" until
      the encryption questions are answered, or until `app.json` carries
      `ITSEncryptionExportComplianceCode` with the key. See
      `ios/export-compliance.md`.
- [ ] `expo-observe` is declared as Performance Data in both the privacy
      manifest and the App Privacy answers. If it is ever removed, change both.
      See `privacy-labels.md`.
- [ ] iPad is off (`supportsTablet: false`), so only iPhone screenshots are
      needed. Turning it on means reviewing every layout at that size.
- [ ] URLs resolve. Privacy policy and marketing point at the docs site,
      support at the repository's issues. Publish the docs site and make the
      repository public before the first submission.
- [ ] Reviewer contact stays a placeholder in `ios/store.config.json` on purpose:
      it is personal and the repository is public. Enter name, email and phone
      in App Store Connect under App Review Information, and skip that section
      when pushing metadata.
- [ ] Screenshots match the build. If onboarding, the chat list or Settings
      changed, the old ones misrepresent the app. Re-run the capture.
- [ ] Exactly the current six screenshots in each store's folder:
      `01-welcome.png`, `02-chats.png`, `03-conversation.png`, `04-note.png`,
      `05-message-actions.png` and `06-plugins.png`, with no stale files beside
      them.
- [ ] The Play feature graphic (1024×500) and 512 icon are in `distribution/play/`,
      regenerated by `npm run brand:build`. Re-run it if the logo changed.

## Android

The same `capture.yaml` drives Android. Its iOS-only prompts are conditional,
and its two `point:` taps (dismissing the keyboard and the message menu) land
on empty space on both platforms.

Build a release APK, so the JavaScript is embedded and no dev client shows.
A local Android build rewrites some libraries' manifests in `node_modules`,
which breaks the next EAS build ("Runtime version mismatch" in
`distribution/README.md`), so build from a worktree with its own copy of
`node_modules`, or run `npm ci` afterwards:

```bash
cd android && ./gradlew :app:assembleRelease -PreactNativeArchitectures=arm64-v8a
emulator -avd pixel &
./scripts/capture-screenshots.sh play android/app/build/outputs/apk/release/app-release.apk
```

The script reinstalls the app with its permissions granted, resizes the
display to 1080×1920 for the run (Play takes only 16:9 or 9:16, and emulators
are 20:9), puts the status bar in demo mode, and resets both on exit. It
collects into `distribution/play/screenshots/` and refuses any other size.
Reinstalling erases whatever app data was on that emulator.

Look at the chat list shot before uploading: a Nostr or Status relay the
emulator cannot reach leaves a "some history unavailable" line above the
chats.

## Push it

`ios/store.config.json` goes up with EAS Metadata. Screenshots are still a manual
upload; EAS Metadata does not handle media.

```bash
npx eas-cli@latest metadata:push   # needs a binary submitted first
```
